# 作業履歴: 年間グラフ目盛り上限の自動算出見直し

## 実施日時
2026-10-08 19:51

## 修正理由・背景
「年間推移・品種別分析」ビューで、自動算出した縦軸の上限が大きすぎ、グラフが小さく見づらいとの指摘を受けた。

- **原単位系（単位本・単位分）の集約グラフ**: 棒の軸上限が「最大品種値 × 2.0」（棒を下半分に抑えて折れ線と分ける設計）で、最大の棒でも軸の 32〜46% にしか届いていなかった。
- **総量系のトレンドグラフ**: 品種単体の線を描くのに、左の積み上げグラフ用の上限（8品種の月計が基準）をそのまま使っており、最大の線でも軸の半分程度までしか届いていなかった。
- 切りの良い値への切り上げ（`getNiceMax`）の幅が最大33%あり、係数を変えるだけでは結果が安定しなかった。

ユーザーに確認した方針:
- 画面の項目は増やさず、既定値の見直しのみ。高さの目安は設定の定数として持つ。
- 原単位系の集約グラフは、最大の棒が軸の約60%、折れ線の最大が約90%。
- 目盛り設定が「固定値」のときも、トレンドグラフ（総量系）はデータから自動算出する。

## 修正内容
1. **高さの目安を設定に追加（`gas_app/js/config.js`、`gas_app/Config.gs`）**
   - `SCALE_CONFIG.autoLayout` を追加（両ファイルに同じ内容）。
     - `rateBarPeakRatio: 0.6`（原単位グラフの棒の最大を置く高さ）
     - `rateLinePeakRatio: 0.9`（原単位グラフの全体平均の折れ線の最大を置く高さ）
     - `trendPeakRatio: 0.9`（トレンドグラフ〔総量系〕の線の最大を置く高さ）

2. **上限の算出関数を追加（`gas_app/js/components/charts.js`）**
   - `getAxisMaxForPeak(peakValue, peakRatio)` を追加し、`ChartManager` から公開。データの最大値が軸の高さの指定割合に来る上限を、切りの良い値へ切り上げる。
   - 切り上げの候補は `getNiceMax` より細かくし、Chart.js の目盛り間隔で割り切れる値だけに限定した。
   - `getNiceMax` は変更していない。

3. **自動算出の見直し（`gas_app/js/app.js` の `getScaleOptions`）**
   - 原単位系（自動）: 棒の軸上限を `getAxisMaxForPeak(品種単体の最大, rateBarPeakRatio)`、折れ線の軸上限を `getAxisMaxForPeak(全体平均の最大, rateLinePeakRatio)` に変更。
   - 総量系（自動・固定とも）: トレンドグラフ専用の上限 `trendMax = getAxisMaxForPeak(品種単体の最大, trendPeakRatio)` を返すようにした。
   - 固定値モードでも `trendMax` を出せるよう、固定値モードの分岐を全年度データの走査の後ろへ移した（固定値モードで返す他の値は従来どおり）。
   - `autoLayout` は `AppConfig.SCALE_CONFIG` から読む。GAS 側の `Config.gs` が古く `autoLayout` を持たない場合は、`js/config.js` の値を使う。

4. **トレンドグラフ側の対応（`gas_app/js/components/charts.js` の `renderAnnualTrendChart`）**
   - y 軸の上限に `scaleOptions.trendMax` を優先して使うようにした（無ければ従来どおり `scaleOptions.max`）。

5. **ドキュメント（`docs/04_実装仕様.md`）**
   - 「2.5 グラフ目盛り上限の決め方」を追加。`AppConfig`・`ChartManager`・`app.js` の説明に追記。

6. **本番成果物の再生成（`gas_app/index.html`）**
   - `node gas_app/build.js` を実行。

## 検証結果
ヘッドレス Chrome で、変更前と変更後の画面を同じ手順（93操作）で操作し、全グラフの軸上限・目盛りラベル・データを採取して比較した。対象は、デモデータ（2024・2025年度、操業モード3種 × 8指標）、目盛り設定「固定値」、実ファイル（2024年7月・10月・2025年3月のロガーデータ + Excel 2本）。

- 変更した軸: 原単位系の集約グラフの左軸・右軸（自動時）、トレンドグラフ（総量系、自動・固定とも）。
- 変更していないグラフ（総量系の集約グラフ、設備別2グラフ、日別グラフ、固定値時の集約グラフ、原単位系表示中のトレンドグラフ）の軸上限は、252軸すべて変更前と同じ。想定外の変化は 0 件。
- 変更した軸の目盛りはすべて等間隔。グラフのデータ自体に差は無い。
- 既存テスト一式（`test_etl_runner.js` → `verify_output.py`、`verify_variety_fixes.js`、`verify_variety_and_restore.js`、`verify_config_sync.js`）: PASSED。

## 補足
- 上限は従来どおり全年度の最大値で統一しているため、値の小さい年度では棒・線が目安より低くなる。上の表の「実データ 2024年度」は、ローカル確認の都合でデモの2025年度データも同時に読み込まれた状態の値で、単位時間の2指標はその影響で低めに出ている（実データだけなら、試算では単位時間電力量の棒の最大は 57% 前後）。
- 切り上げの候補は、当初の計画（隣り合う候補の比が最大約1.17）より粗い、最大1.25のものにした。計画どおりの候補では、最上段の目盛りだけ間隔が詰まる（例: `12.00` の次が `13.00`）ことが検証で分かったため、Chart.js の目盛り間隔で割り切れる値だけに絞った。その結果、データの最大値の位置は、棒が軸の 48〜60%、線が 72〜90% の範囲になる。
- 固定値モードの集約グラフ（原単位系の折れ線が設定値 × 0.6 になる点を含む）は変更していない。
- 実際の GAS 環境での確認は未実施。`Config.gs` と `index.html` を貼り替えて再デプロイする必要がある（`Code.gs` は今回変更なし）。`Config.gs` を貼り替えなくても、`index.html` 側の値で動作する。
